# GlobeGuide 全球旅行信息平台设计

日期：2026-10-19  
状态：待用户评审

## 1. 产品定义

GlobeGuide 是面向全球用户的旅行信息与社区平台。它把官方资料、平台编辑内容和用户实地经验组织到统一的地点体系中，并通过搜索、推荐和 AI 行程规划帮助用户做旅行决策。

首期核心场景是：用户已经决定前往某个目的地，希望在一个地方获得完整、可信、及时的信息，并将内容保存为可执行的旅行计划。

平台从第一天支持全球地点、语言、时区和币种，但首期只由平台主动维护东京、巴黎和纽约三个目的地。用户仍可搜索、创建和发布其他全球地点的内容。

## 2. 设计原则

1. 全球数据模型，分阶段部署和运营。
2. Web 负责搜索获客与深度阅读，移动 App 负责贡献、留存和旅行中使用。
3. 用户内容围绕地点组织，不能成为与目的地脱节的信息流。
4. 原始事实、用户经验、翻译和 AI 结论必须分开存储。
5. 事实信息必须保留来源、采集时间、适用时间和可信度。
6. 早期采用规则推荐；有足够行为数据后再引入学习排序。
7. 先做模块化单体，不提前承担微服务和全球多活成本。

## 3. 第一阶段范围

### 3.1 用户能力

- 使用邮箱、Apple 或 Google 登录。
- 设置界面语言、常住地区、熟悉的地点和感兴趣的目的地。
- 搜索国家、城市、区域和地点。
- 浏览目的地聚合页、地点详情、官方信息和社区经验。
- 发布包含文字、图片、地点、访问时间、花费和标签的旅行内容。
- 对信息执行点赞、收藏、评论、举报、纠错和“近期仍有效”确认。
- 创建旅行清单，把地点或帖子加入计划。
- 输入日期、预算、同行人员和偏好，生成可编辑的 AI 日程草案。
- 在移动端缓存已保存行程，接收与行程相关的通知。

### 3.2 运营能力

- 管理全球地点层级和重复地点合并。
- 发布并更新官方信息，记录原始来源和有效期。
- 审核用户内容、举报和地点修改建议。
- 查看内容新鲜度、目的地覆盖率和高风险冲突。
- 对机器翻译和 AI 提取结果进行人工复核。

### 3.3 明确不做

- 不在第一阶段自营机票、酒店或旅游套餐交易。
- 不做 Windows、macOS 或 Linux 原生桌面客户端；PC 使用 Web。
- 不做直播、私信、短视频剪辑和泛社交关系链。
- 不训练自有大语言模型或推荐基础模型。
- 不建设微服务、Kubernetes 或跨洲多主数据库。
- 不在第一阶段建设中国大陆独立部署；通过供应商适配层保留后续能力。

## 4. 核心用户流程

### 4.1 目的地搜索

1. 用户搜索城市、地点或旅行问题。
2. 搜索服务识别语言、地点实体和意图。
3. 结果混合展示目的地、地点、官方信息和社区内容。
4. 排序考虑文本相关性、地理相关性、可信度、新鲜度和个性化信号。
5. 用户进入目的地页后，可筛选主题、人群、预算、季节和内容来源。

### 4.2 内容贡献

1. 用户选择或创建地点。
2. 用户发布旅行经验并提供访问时间、花费和适用标签。
3. 系统执行安全审核、垃圾识别、语言检测和地点实体提取。
4. 内容通过后进入地点页和符合条件用户的推荐候选集。
5. AI 可以提出结构化字段，但作者必须确认后才能成为事实候选。

### 4.3 信息纠错

1. 用户针对具体字段提交修改，不直接覆盖原记录。
2. 系统保留修改前后的值、证据、提交者和时间。
3. 官方来源更新可直接进入审核队列；社区修改按信誉和多方确认排序。
4. 审核通过后生成新版本，旧版本继续用于审计。

### 4.4 AI 行程规划

1. 用户提供目的地、日期、预算、同行人员、节奏和兴趣。
2. 系统从地点、官方事实和高质量社区内容中检索候选。
3. 规则层先过滤关闭、时间冲突、不适合和距离不合理的地点。
4. AI 只负责组合、解释和生成自然语言，不直接创造事实。
5. 输出包含来源、更新时间和不确定性提示，并允许用户拖拽修改。

## 5. 信息架构与数据模型

### 5.1 地点图谱

地点采用稳定的全球唯一 ID，并使用以下层级：

`World -> Country/Region -> Administrative Area -> City -> District -> Place`

核心实体包括：

- `Place`：名称、别名、坐标、地址、类别、时区、状态。
- `PlaceName`：语言、文字系统、规范名称和搜索别名。
- `PlaceRelation`：行政隶属、邻近、位于内部和交通连接。
- `Source`：官方机构、网址、许可、抓取或人工录入方式。
- `Fact`：营业时间、票价、交通、规则、安全等结构化事实。
- `FactVersion`：事实变更、证据、有效期、确认时间和审核状态。

### 5.2 内容与社区

- `Post`：用户经验的原始内容，始终保留原始语言。
- `PostTranslation`：机器或人工翻译，与原文分离并记录版本。
- `MediaAsset`：图片或视频、版权归属、审核状态和派生尺寸。
- `Comment`、`Reaction`、`Collection`：社区互动。
- `Correction`：针对事实、地点或内容的结构化修正建议。
- `Verification`：用户对特定事实在特定时间仍有效的确认。
- `Report`、`ModerationCase`：举报、处理动作和审计记录。

### 5.3 用户与信誉

- `UserProfile`：语言、常住地区、旅行偏好和隐私设置。
- `Expertise`：用户熟悉的地点、依据和最近访问时间。
- `ReputationEvent`：内容被采纳、纠错准确、举报成立等事件。
- `TrustScore`：按地点和主题计算的可解释分数，不使用单一永久总分。

### 5.4 行程

- `Trip`：目的地、日期、时区、参与者和预算。
- `TripItem`：地点、开始时间、时长、交通和来源。
- `TripRevision`：人工或 AI 调整后的版本历史。
- `SavedItem`：用户收藏但尚未排入时间表的内容。

## 6. 技术架构

### 6.1 Monorepo

使用 pnpm workspace 和 Turborepo：

```text
apps/
  web/          Next.js Web、PWA、SEO 和运营后台入口
  mobile/       Expo / React Native，构建 iOS 与 Android
  api/          NestJS + Fastify，REST/OpenAPI 与 WebSocket
  worker/       审核、翻译、索引、通知和媒体异步任务
packages/
  domain/       领域类型、值对象和共享校验规则
  api-client/   根据 OpenAPI 生成的类型安全客户端
  ui/           设计令牌与可共享的无业务 UI 原语
  i18n/         locale、语言、时区、币种和格式化规则
  config/       TypeScript、ESLint、测试和构建配置
```

Web 与 Mobile 共用领域类型、API 客户端、设计令牌和国际化资源，不强求共享所有 UI 组件。

### 6.2 后端模块

`api` 是一个模块化单体，包含明确的内部模块：

- Identity：登录、会话、设备和权限。
- Geography：地点图谱、别名、合并与地理查询。
- Publishing：帖子、媒体、草稿和翻译。
- Knowledge：来源、事实、版本、确认和纠错。
- Community：评论、反应、收藏和举报。
- Search：查询理解、召回和结果聚合。
- Recommendation：候选生成、打分、探索和反馈。
- Trips：旅行清单、日程、协作和版本。
- AI：模型供应商、检索、提示模板和安全边界。
- Moderation：自动检测、人工队列、动作和申诉。
- Notifications：站内、邮件和移动推送。
- Admin：运营、审计和质量仪表盘。

模块只能通过公开应用服务或领域事件交互，不能跨模块直接修改数据表。耗时操作使用事务型 Outbox 发布到任务队列。

### 6.3 基础设施

- PostgreSQL + PostGIS：业务数据、地点和地理查询。
- Redis：缓存、限流、短期状态和幂等键。
- OpenSearch：多语言全文检索、地理召回和推荐候选。
- S3 兼容对象存储：原始媒体和处理后的派生文件。
- CDN：Web 静态资源、公开图片和视频。
- 队列：开发环境使用 Redis 队列；生产可替换为云托管队列。
- OpenTelemetry：日志、指标、追踪和关联 ID。

第一阶段部署在单一主区域，公开页面和媒体通过全球 CDN 分发。数据库每日备份并进行恢复演练。区域化接口保留 `data_region` 和供应商适配器，但不实现跨区域多活。

## 7. API 与客户端策略

- 对客户端提供版本化 REST API，并生成 OpenAPI 文档和客户端。
- 评论更新、审核状态和通知使用 WebSocket；断线后通过游标补拉。
- 所有创建或支付类请求支持幂等键。
- 列表统一采用基于游标的分页。
- API 返回稳定错误码、面向用户的本地化消息键和关联 ID。
- Web 使用服务端渲染公开目的地页；用户区使用客户端交互。
- Mobile 使用本地数据库缓存行程、地点摘要和待上传草稿。

## 8. 搜索与推荐

### 8.1 搜索

索引保留原文、多语言名称、翻译、地点层级、时间和来源类型。查询流程为语言识别、地点实体识别、关键词召回、地理召回、过滤和重排。

### 8.2 第一阶段推荐

不训练机器学习模型。候选打分由以下可解释特征组成：

- 与当前目的地及旅行日期的相关性。
- 信息来源和作者在该地点的可信度。
- 发布时间、访问时间、最近确认时间和有效期。
- 收藏、加入行程、评论质量和举报率。
- 用户的语言、预算、兴趣、同行人员和旅行节奏。
- 多样性约束，避免结果全部来自同一作者或热门地点。

系统必须记录曝光、点击、收藏、加入行程、隐藏、举报和实际确认事件。只有在连续四周累计至少 100,000 次有效推荐曝光和 10,000 次正向行为后，才评估增加向量召回；学习排序还必须通过离线回放和小流量 A/B 测试。规则分始终作为安全与质量约束。

## 9. AI 边界

- 模型供应商通过统一接口接入，允许按区域、价格和能力切换。
- 检索到的事实包含来源、版本和有效期。
- AI 输出使用结构化 Schema 校验，失败时重试或降级为普通搜索结果。
- 签证、安全、健康和法律信息只摘要官方来源，并明确提示用户核验。
- 自动翻译不覆盖原文，用户可查看原文和翻译来源。
- 所有提示模板、模型、输入来源和输出版本可审计。

## 10. 可信度与内容治理

内容展示明确区分：官方资料、平台编辑、当地贡献者、近期旅行者和 AI 摘要。

可信度不是一个不可解释的全局分数，而由来源等级、证据、作者地点信誉、社区确认、新鲜度和冲突情况组成。存在冲突时展示差异和各自时间，不让 AI 静默选择答案。

发布流程包括垃圾内容、恶意链接、成人内容、仇恨骚扰、个人隐私和版权风险检测。高风险类别必须进入人工审核。用户可以举报、申诉、屏蔽作者和删除自己的数据。

## 11. 国际化与区域适配

- 英语为首发界面语言，代码不得硬编码展示文案。
- 数据库保存 BCP 47 locale、IANA 时区和 ISO 货币代码。
- 日期、数字、货币、距离和温度根据 locale 格式化。
- 右到左布局从设计令牌和布局层支持，但首期不提供阿拉伯语界面。
- 地图、登录、支付、翻译、推送和邮件均通过供应商接口接入。
- 中国大陆独立部署属于后续项目，需要单独评估备案、地图坐标、内容审核、数据跨境和本地供应商。

## 12. 安全、隐私与合规

- 默认最小化收集个人信息；精确位置需要单独授权且可随时关闭。
- 密码不由业务服务直接保存；认证遵循 OIDC/OAuth 2.1。
- 访问控制采用角色与资源所有权组合，后台强制多因素认证。
- 上传文件校验类型、大小并执行恶意内容扫描。
- 用户输入、翻译内容和 AI 输出都不得直接进入富文本或查询语句。
- 对登录、发布、评论、搜索和 AI 调用分别限流。
- 提供数据导出、删除、同意记录、保留策略和审计日志。
- 第一阶段隐私流程以 GDPR 和 CCPA 的基本要求为基线，正式上线前进行法律评审。

## 13. 错误处理与降级

- 搜索不可用时回退到数据库中的热门目的地和精确地点匹配。
- AI 不可用时仍可完成搜索、浏览、发布、收藏和手工行程。
- 翻译失败时展示原文并允许稍后重试。
- 媒体处理失败不丢失草稿，客户端显示可恢复状态。
- 队列任务使用有限重试、指数退避和死信队列。
- 第三方地图或登录供应商故障通过适配器隔离并记录状态。
- 所有可重试写操作使用幂等键，避免重复帖子或行程项。

## 14. 测试与质量

- Domain：地点层级、时间、货币、可信度和行程规则的单元测试。
- API：模块集成测试、权限测试和 OpenAPI 契约测试。
- Web：关键公开页的可访问性、SEO 和 Playwright 流程测试。
- Mobile：登录、发布、收藏、离线行程和同步的设备级测试。
- Search：固定语料的相关性回归测试，多语言名称不得退化。
- Recommendation：离线样本验证过滤、可信度和多样性约束。
- AI：结构化输出、引用完整性、危险建议和提示注入测试。
- Operations：备份恢复、队列重放和降级演练。

## 15. 第一阶段交付拆分

### Milestone 1：工程与领域基础

Monorepo、CI、Web、Mobile、API、数据库、认证、国际化、可观测性和全球地点核心模型。

### Milestone 2：目的地与内容闭环

目的地搜索、目的地页、地点页、官方事实、用户发帖、媒体、评论、收藏、纠错和后台审核。

### Milestone 3：搜索、推荐与行程

OpenSearch、规则推荐、旅行清单、日程编辑、离线缓存和通知。

### Milestone 4：AI 与公测准备

带引用的问答、行程草案、内容结构化、翻译、质量仪表盘、安全测试和首批城市内容导入。

## 16. 验收标准

- Web、iOS 和 Android 使用同一账号和后端数据。
- 用户可以从搜索进入目的地，阅读官方与社区信息，发布内容并加入行程。
- 公开地点和目的地页面可被搜索引擎索引并包含正确结构化数据。
- 原始内容、翻译、事实和 AI 摘要在存储及界面上可区分。
- 规则推荐能够解释主要排序原因，并执行新鲜度和多样性约束。
- AI 行程中的关键地点和事实都能追溯到来源。
- 核心流程在 AI、翻译或搜索单项故障时仍可使用。
- 自动化测试覆盖核心领域规则、权限边界和关键端到端流程。

## 17. 成功指标

公测阶段重点观察：

- 搜索后进入有效目的地或地点页面的比例。
- 目的地页到收藏或加入行程的转化率。
- 行程创建完成率和旅行前再次访问率。
- 有效内容贡献率、纠错采纳率和事实近期确认率。
- 严重事实错误率、举报成立率和审核处理时间。
- Web 获客后转化为注册和 App 激活的比例。

这些指标用于决定是否扩大目的地、增加客户端功能或升级推荐算法，不以注册用户总量作为唯一判断标准。
